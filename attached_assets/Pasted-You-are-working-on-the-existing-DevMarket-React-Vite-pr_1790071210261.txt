IMPORTANT ARCHITECTURE:

DevMarket uses a HYBRID database architecture.

FIREBASE:

* Firebase Authentication remains the authentication system.
* Firebase Firestore remains responsible for user-owned/personal data such as:
    * users/profile data
    * settings
    * favorites/saved items
    * other personal user data that already uses Firestore
* Do NOT migrate these systems to Supabase.
* Do NOT replace Firebase Authentication.

SUPABASE:

* Supabase PostgreSQL is responsible for DevMarket’s shared product/library data and future Builder data.
* The existing Supabase project is already created and its schema has already been configured.
* Do NOT create another Supabase project.
* Do NOT recreate or delete the existing tables.
* Inspect the existing schema before making changes.

SUPABASE LIBRARY TABLES:

Existing tables include:

* categories
* components
* tags
* component_tags
* templates

Categories represent sections of the public library.

Components contain metadata only. A component card must NOT contain the actual React source code directly.

A component record contains information such as:

* id
* name
* slug
* type
* description
* category_id
* status
* is_vip
* preview_url
* code_reference
* timestamps

The component ID is the connection between the public card and the actual component.

Tags are related to components through component_tags.

VIP components are identified through the existing is_vip field and/or tags.

Categories now also support:

* section_type
* is_under_construction
* display_order
* is_active

Use these fields to determine where components appear.

PUBLIC LIBRARY BEHAVIOR:

Create the library so that component data is loaded from Supabase rather than hardcoded into JSX.

The flow should be:

Supabase
→ fetch categories/sections
→ fetch published components
→ fetch component/tag relationships as needed
→ group components into their appropriate sections
→ render a reusable ComponentCard for each component

Do NOT create a separate hardcoded component list for every section.

The section/category data should determine where content appears.

For example:

* A category can represent a normal component section.
* A VIP section can be marked as VIP/under construction.
* A category marked is_under_construction should display the appropriate under-construction UI rather than pretending it has available components.
* display_order determines section ordering.

COMPONENT CARD:

Create a reusable ComponentCard component.

The card should be driven by component metadata from Supabase.

It should support the basic information required for the library:

* component name
* description
* preview
* category/type information where appropriate
* tags where appropriate
* VIP indication where appropriate
* download action
* details/view action

DO NOT put the actual React source code directly into the card component.

The card should receive a component record and use its ID/code_reference to determine what code/resource it belongs to.

The download system can initially use the existing code_reference field as the source/reference for the actual component files.

Keep the actual component source separate from the UI card metadata.
