Code Companion — Phase 1: Account Reliability and Settings

Objective

Fix the confirmed account-flow bugs and make the Settings page reliable for the first release. Work from the current project, including the latest changes pulled from Codex.

The pre-release audit identified:

1. Failed email/password login and signup attempts navigate away from their error messages.
2. Password-reset error handling references an undefined variable.
3. Settings controls are mostly nonfunctional.
4. The Settings route has no authentication guard.
5. The Login page exposes development diagnostics.

Scope

1. Fix email/password authentication feedback

Inspect public/src/components/authUI/LoginForm.jsx and SignupForm.jsx.

* Navigate only after successful authentication.
* Keep users on the form after failed attempts.
* Display useful, user-safe error messages.
* Preserve existing Firebase authentication methods and context integration.
* Prevent duplicate submissions while an operation is in progress if this is not already handled.
* Do not change Google OAuth behavior or configuration.

2. Fix password-reset error handling

Inspect public/src/pages/ResetPassword.jsx.

* Fix the undefined error-variable reference.
* Preserve appropriate handling for expired or invalid reset links and weak passwords.
* Display errors clearly without exposing sensitive implementation details.
* Preserve the existing Firebase password-reset flow.
* Do not claim success if the operation fails.

3. Complete the Settings page for v1

Inspect public/src/pages/Settings.jsx, public/src/context/AuthContext.jsx, and public/src/services/settingsService.js before making changes.

Implement the following:

* Theme selection must reflect the current theme and persist through the existing settings service.
* Logout must use the existing authentication context/service and return the user to an appropriate signed-out state.
* Change Password should work for supported email/password accounts, with suitable validation and Firebase reauthentication where required. If this cannot be safely completed within the existing architecture, disable or remove the control and report why.
* Change Email may be deferred. Do not leave a misleading, nonfunctional button.
* Delete Account may be deferred. Do not implement a superficial deletion flow that leaves account data behind or bypasses reauthentication.
* Support and policy links must point to real existing destinations. If the pages do not exist yet, use an honest disabled or clearly deferred presentation rather than fake links.
* Add appropriate loading, success, and error states.
* Preserve the existing Firebase/Firestore ownership model for user-specific settings.
* Do not move user settings into Supabase.

Decide whether /settings requires authentication by examining existing routing and navigation patterns. If it is a private account page, apply the smallest consistent route-protection change and ensure signed-out users receive a clear path to log in. Do not introduce a new authentication architecture.

4. Remove development diagnostics

Inspect public/src/pages/Login.jsx.

* Remove the user-facing diagnostic block that displays authentication state, profile status, or the current origin.
* Keep any necessary diagnostics out of the production-facing UI.
* Do not expose a user’s email or account state unnecessarily.

5. Preserve architecture and boundaries

* React + Vite and React Router remain unchanged.
* Firebase remains responsible for authentication and user-specific data.
* Supabase remains responsible for the shared component library and future Builder data.
* Do not use Next.js or migrate frameworks.
* Do not redesign the entire application in this phase.
* Do not rebuild or regenerate the component library, ZIP packages, previews, or Supabase metadata unless a scoped change makes it strictly necessary.
* Do not investigate, debug, reconfigure, or attempt to fix Google OAuth. Its current URL configuration is known to be incompatible; leave it untouched.
* Do not change production Firebase or Supabase settings, security rules, or live data as part of this task.

6. Validation

* Run the existing frontend build and relevant available tests.
* Verify failed login/signup submissions stay on their forms and retain their errors.
* Verify password-reset failures display errors rather than throwing.
* Verify theme persistence and logout behavior using available safe test methods.
* Check that Settings access behaves correctly for signed-in and signed-out users.
* Do not claim live Firebase behavior has been verified unless it was actually tested.
* Do not fix unrelated warnings or reconfigure the environment.

7. Report and stopping conditions

At completion, report:

* Files changed and the purpose of each change.
* Which requirements were completed, deferred, or blocked.
* Build/test results and what was not testable.
* Any Firebase reauthentication or account-deletion limitations.
* Confirmation that Google OAuth configuration and behavior were left untouched.
* Any remaining first-release blockers.

Do not commit, push, or deploy. Do not begin the broader UI/UX redesign or additional component work. Finish this phase, report the results, and stop for review.
