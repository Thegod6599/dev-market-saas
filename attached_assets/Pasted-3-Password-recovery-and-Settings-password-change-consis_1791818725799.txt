3. Password recovery and Settings password-change consistency

Inspect public/src/pages/ResetPassword.jsx, the password-reset link in public/src/components/authUI/LoginForm.jsx, and the Change Password control in public/src/pages/Settings.jsx.

A. Password reset from Login

* Verify how the existing password-reset link generates or opens the reset flow.
* Inspect how the reset URL is constructed and how ResetPassword.jsx reads the action code and applies the new password.
* Check whether the current development or deployment domain must be added to Firebase Authentication’s authorized domains.
* Do not assume a frontend code change can fix an unauthorized domain.
* If Firebase configuration is the blocker, report the exact configuration that needs attention and the appropriate domain, without changing live Firebase settings or inventing a domain.
* Preserve Firebase’s existing password-reset mechanism. Do not expose API keys, reset codes, or other sensitive values in user-facing diagnostics.
* Ensure success and failure messages are visible and that a successful reset leads to an appropriate login state.

B. Align ResetPassword with Settings

Make ResetPassword.jsx consistent with the Change Password experience in Settings in terms of:

* Page layout and visual styling
* Form labels, password fields, validation, and feedback
* Loading and submission states
* Error handling and accessible controls

Reuse existing styles or shared components where sensible rather than duplicating large amounts of code.

However, preserve the distinction between the two flows:

1. Forgot password: A signed-out user requests an email, opens Firebase’s password-reset link, and submits a new password using the valid reset action code.
2. Change password: A signed-in user opens Settings and changes their password through Firebase’s authenticated account flow, including reauthentication when required.

Do not make the Settings button send users into a reset flow that requires an email if the intended action is an authenticated password change. Conversely, do not make the reset page require an authenticated session when Firebase’s valid reset action code is intended to authorize the password reset.

If the existing Firebase action-code configuration supports a custom continuation URL or action handler, inspect the current implementation and use the smallest compatible approach. Do not introduce a new authentication system or change the application’s framework.

C. Verification

* Verify the Login page’s password-reset link destination.
* Test the reset page’s handling of missing, invalid, expired, and valid action codes where safely possible.
* Confirm that a failed reset shows a useful error rather than throwing an exception.
* Verify the Settings Change Password action separately from the email-reset flow.
* Distinguish code-level verification from a real email round-trip test.
* If the current project URL is not authorized in Firebase, mark the live reset flow as blocked pending Firebase configuration. Do not claim the issue is fixed merely because the page builds.

Do not modify Google OAuth configuration or behavior.
